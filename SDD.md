## 1. System Architecture

```
┌──────────────────────────────────────────────────────────────┐
│                          CLIENT                                │
│  Next.js App Router (React Server + Client Components)         │
│  Tailwind (latest) + shadcn/ui | Framer Motion (journey path)  │
│  TanStack Query (server state) | React Context (language,      │
│  selected center — small global UI state only)                 │
│  Google Drive Picker (client-side video upload widget)         │
└───────────────────────────┬──────────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼──────────────────────────────────┐
│                        API LAYER                                │
│  Next.js Route Handlers (/api/*)                                │
│  Auth: Supabase JWT verification (middleware.ts)                │
│  Validation: Zod schemas on every request body                  │
│  Server-only: Claude API key, Google Drive API key, PDF render  │
└───────┬───────────────────────┬─────────────────┬──────────────┘
        │                       │                 │
┌───────▼──────────┐  ┌─────────▼─────────┐ ┌─────▼──────────────┐
│  SUPABASE         │  │  GOOGLE DRIVE API  │ │  ANTHROPIC API      │
│  Postgres + RLS   │  │  Video storage —   │ │  Claude — AI report │
│  Supabase Auth    │  │  link only, never  │ │  text drafting,     │
│  (email/password  │  │  raw bytes in DB   │ │  server-side only   │
│  for staff, magic  │  └────────────────────┘ └──────────────────┘
│  link for parent/  │
│  student)          │
│  Supabase Storage  │
│  (generated PDF     │
│  reports only —    │
│  small files)       │
└─────────────────────┘
```

**Why this shape:** Video never touches the server or the database as bytes — Drive Picker runs client-side, the server only ever stores a file ID and link. This keeps the zero-budget Vercel/Supabase free tiers from ever being threatened by video bandwidth, which was flagged as the single biggest infra risk back in the BRD.

## 2. Service Boundaries

### Runs on CLIENT (browser)
- UI rendering and interaction (Next.js Client Components)
- Journey path rendering and node animations (Framer Motion)
- Google Drive Picker widget (video selection/upload — Google's own client SDK, not KOMS's server)
- Client-side form validation (UX feedback only — never the security boundary)
- Optimistic UI updates (attendance toggles, lesson-complete checkboxes)
- Language toggle (EN/ID) — stored in a cookie, read by middleware for SSR locale

### Runs on SERVER (Next.js Route Handlers)
- All DB queries (never direct client-to-Supabase writes for anything beyond what RLS already scopes — reads can go client-to-Supabase via the JS client since RLS is the real boundary, but writes with side effects, like sending an invite email, always go through a Route Handler)
- Supabase Auth token verification
- Claude API calls (AI report drafting) — API key is server-only, never shipped to the client
- Google Drive file-ID → shareable-link resolution (confirming the link is valid/accessible before saving)
- PDF rendering (`@react-pdf/renderer` — pure JS, runs fine in Vercel serverless, unlike headless-Chrome options which are too heavy for this infra)
- Parent/teacher invite emails (Supabase Auth `inviteUserByEmail` / magic link send)

### Runs on EDGE (middleware.ts)
- Auth session check → redirects unauthenticated users to the correct login (`/login` for staff, `/student/login` for parent/student)
- Route-group protection: `/admin/*` requires `role = 'admin'`, `/dashboard/*` requires `role = 'teacher'` or `'admin'`, `/student/*` requires `role = 'parent'`
- Locale cookie read → sets response locale before render

### Runs in DATABASE (Supabase)
- RLS enforcement — this is the actual security boundary for every table, not the API layer's job to re-check
- No triggers in v1 — kept deliberately simple given the timeline
- No computed columns — lesson totals and progress counts are computed in queries (`COUNT`), not stored, to avoid a second source of truth

## 3. API Contracts

### POST /api/auth/staff-login
**Purpose:** Teacher/Admin email+password login
**Auth:** `public`
**Request:**
```typescript
interface StaffLoginRequest {
  email: string
  password: string
}
```
**Response (200):**
```typescript
interface StaffLoginResponse {
  redirectTo: '/dashboard' | '/admin'
}
```
**Errors:**
| Code | Condition | Message |
|------|-----------|---------|
| 400 | Missing email or password | "Enter an email and password" |
| 401 | Wrong credentials | "Invalid email or password" |
| 500 | Supabase error | "Internal server error" |

**DB operation:** `supabase.auth.signInWithPassword({ email, password })`, then `SELECT role FROM users WHERE id = auth.uid()`
**Used by screen:** Login

### PATCH /api/sessions/:id/log
**Purpose:** The core write — record attendance, video, lesson completion, and notes for a session in one submit
**Auth:** `role: teacher` (must own the session)
**Request:**
```typescript
interface LogSessionRequest {
  attendance: Array<{ studentId: string; status: 'present' | 'absent' }>
  video?: { driveFileId: string; driveLink: string }
  notes?: string
  lessonCompletions: Array<{ studentId: string; lessonId: string }>
}
```
**Response (200):**
```typescript
interface LogSessionResponse {
  sessionId: string
  status: 'completed'
}
```
**Errors:**
| Code | Condition | Message |
|------|-----------|---------|
| 403 | Session not owned by requester | "Not authorized" |
| 404 | Session not found | "Session not found" |
| 500 | Partial write failure | "Internal server error" — session-level fields still saved even if video insert fails (see below) |

**DB operation (in order, video failure is non-blocking per PRD edge case):**
```sql
UPDATE sessions SET status = 'completed', notes = $notes WHERE id = $sessionId;
INSERT INTO attendance (session_id, student_id, status) VALUES (...) ON CONFLICT (session_id, student_id) DO UPDATE SET status = excluded.status;
INSERT INTO session_videos (session_id, drive_file_id, drive_link) VALUES (...); -- wrapped separately, failure doesn't roll back the above
INSERT INTO student_lesson_progress (student_id, lesson_id, status, session_id, completed_date)
  VALUES (..., 'completed', $sessionId, now())
  ON CONFLICT (student_id, lesson_id) DO UPDATE SET status = 'completed', session_id = excluded.session_id, completed_date = excluded.completed_date;
```
**Used by screen:** Log Session

## 4. Auth Flow

### Staff account creation (Teacher/Admin)
1. Admin submits `{ name, email }` via Manage Teachers
2. Server calls `supabase.auth.admin.inviteUserByEmail(email)` — Supabase sends a set-password invite link
3. Server creates a `public.users` row with `role='teacher'`, `center_id` = admin's active center, linked to the new `auth.users.id` once the invite is accepted (webhook or on first login upsert)
4. Teacher clicks the invite link → sets a password → redirected to `/dashboard`

### Staff login
1. User submits `{ email, password }`
2. Server calls `supabase.auth.signInWithPassword()`
3. On success: session cookie set, `SELECT role FROM users WHERE id = auth.uid()` determines redirect (`/dashboard` for teacher, `/admin` for admin — Gio gets both, lands on `/dashboard` with an admin nav link visible)
4. On failure: `{ error: "Invalid email or password" }` — never reveal which field is wrong

### Parent/Student login (magic link)
1. User submits `{ email }`
2. Server checks the email is linked to a student (`role='parent'` row exists) — if not, clear error, no link sent
3. `supabase.auth.signInWithOtp({ email })` — Supabase emails the magic link
4. User clicks it → session established → redirected to `/student/:id` (auto if one child) or a student switcher (if multiple)

### Session persistence
- `middleware.ts` runs on every request
- Reads the Supabase session cookie
- Valid → attaches `{ userId, role }` to request context, continues
- Expired → attempts refresh → failure redirects to the correct login for that route group
- Missing → `/dashboard/*` and `/admin/*` redirect to `/login`; `/student/*` redirects to `/student/login`

### Logout
1. Client calls `POST /api/auth/logout`
2. Server calls `supabase.auth.signOut()`
3. Session cookie cleared, redirect to `/`

### Protected routes
- `/dashboard/*` — role: teacher or admin
- `/admin/*` — role: admin only
- `/student/*` — role: parent only
- Public: `/`, `/login`, `/student/login`

## 5. Key Data Flows

### Flow: Log a session (attendance + video + lesson completion)
*Persona: Teacher | Starts at: My Schedule or Class Roster | Goal: one session fully documented*

1. **User action:** Teacher taps a scheduled session, opens Log Session
2. **Client:** Roster loads via `GET /api/classes/:id/roster`; attendance toggles default to unmarked, optimistic UI on toggle
3. **User action:** Marks attendance, opens Drive Picker (client-side), selects/uploads video, checks off completed lessons per student, writes notes
4. **API call:** `PATCH /api/sessions/:id/log` with the full payload (attendance, video ref, lessonCompletions, notes)
5. **Middleware:** confirms `role: teacher`
6. **Server validation:** Zod schema — at least one attendance entry recommended (warn, not block, per PRD edge case)
7. **DB operation:** session UPDATE, attendance UPSERT, session_videos INSERT (non-blocking on failure), student_lesson_progress UPSERT
8. **RLS check:** `sessions_all_teacher`, `attendance_all_teacher`, `progress_all_teacher` — all scoped to `teacher_id = auth.uid()`
9. **Server response:** `{ sessionId, status: 'completed' }`
10. **Client update:** redirect to Dashboard with a confirmation toast; Journey view for affected students will reflect new node states next time it's fetched (TanStack Query cache invalidated on `classId`)
11. **Error path:** if video insert fails, session/attendance/progress still saved — client shows "Saved, but video didn't attach — retry from Student Detail"

### Flow: Generate an AI-assisted report
*Persona: Teacher | Starts at: Student Detail | Goal: polished PDF report*

1. **User action:** Taps "Generate Report" on Student Detail
2. **Client:** navigates to Generate Report, pre-fetches lesson/attendance summary
3. **User action:** writes rough notes, taps "Draft with AI"
4. **API call:** `POST /api/students/:id/report/draft` with `{ classId, rawNotes }`
5. **Server validation:** confirms student belongs to requester's class
6. **Server operation:** builds a prompt from the fetched summary + rawNotes, calls Anthropic API server-side
7. **Server response:** `{ draftText }`
8. **Client update:** populates an editable text field — never auto-exports
9. **User action:** edits if needed, taps "Export PDF"
10. **API call:** `POST /api/students/:id/report/export` with `{ classId, finalText, templateId }`
11. **DB operation:** render PDF, upload to Supabase Storage, `INSERT INTO reports`
12. **Client update:** confirmation, report now visible on the student's Student Profile (parent side) immediately
13. **Error path:** AI draft failure (502) → client shows "Couldn't generate a draft — write manually," rawNotes stays in the field, export path still works with hand-typed text

### Flow: Parent views the Journey
*Persona: Parent | Starts at: Student/Parent Login | Goal: see their child's actual curriculum progress*

1. **User action:** submits email on Student/Parent Login
2. **API call:** `POST /api/auth/magic-link`
3. **Server validation:** email must match a `role='parent'` user linked via `student_guardians`
4. **User action:** clicks the emailed link → session established
5. **Client:** `GET /api/student/profile` → renders Student Profile (avatar, active/completed program cards)
6. **User action:** taps an active program card
7. **API call:** `GET /api/student/:id/journey/:classId`
8. **RLS check:** `lessons_select_parent`, `progress_select_parent` — both traverse through `student_guardians.guardian_id = auth.uid()`
9. **Client update:** Framer Motion renders the snake path, node states colored by status
10. **Error path:** no lesson plan defined yet for that class → empty state, not a broken render

### Flow: Admin builds a lesson plan
*Persona: Admin (Gio) | Starts at: Manage Lesson Plan | Goal: curriculum template that generates every student's journey*

1. **User action:** navigates to a class's Manage Lesson Plan screen
2. **Client:** `GET /api/admin/classes/:id/lessons`
3. **User action:** adds lessons one at a time (title, description)
4. **API call:** `POST /api/admin/classes/:id/lessons` per lesson — `sequence_number` auto-increments server-side
5. **Client update:** list re-renders in order; no separate "publish" step — a lesson is live the moment it's created, since every student's Journey query reads `lessons` directly
6. **Error path:** deleting a lesson with existing completions → server returns `studentsAffected` count → client shows a confirm dialog naming the number before the DELETE call fires

## 6. Third-Party Integrations

### Supabase (Auth + Postgres + Storage)
**Purpose:** Auth (staff password, parent/student magic link), the entire database, and storage for generated PDF reports only
**SDK:** `@supabase/supabase-js`, `@supabase/ssr` (for Next.js App Router server/client split)
**Auth method:** Service role key server-only for admin operations (`inviteUserByEmail`); anon key + RLS for regular client reads
**Called from:** both — reads via client SDK (RLS-protected), invite/admin operations server-only
**Key operations:**
  - `signInWithPassword` / `signInWithOtp`: login
  - `auth.admin.inviteUserByEmail`: teacher and parent invites
  - Storage `upload`/`createSignedUrl`: report PDFs
**Failure handling:** Supabase down → generic 500, no silent data loss since every write is a single transaction per request

### Google Drive API + Picker
**Purpose:** Video storage for session documentation — KOMS never holds video bytes
**SDK:** Google Picker API (client-side, `gapi` script) + Drive API v3 (server-side, to confirm link validity)
**Auth method:** Google OAuth (Gio's own Google account for v1 — Drive files live in his Drive, shared via link)
**Called from:** Picker is client-only; link validation is server-only
**Key operations:**
  - Picker: teacher selects/uploads a video, returns `{ fileId, url }`
  - Server: confirms the file is shared appropriately before saving `session_videos`
**Failure handling:** Picker failure → session still saves without video (non-blocking, per PRD edge case); video can be attached later from Student Detail

### Anthropic API (Claude)
**Purpose:** Drafts report text from a teacher's rough notes
**SDK:** `@anthropic-ai/sdk`
**Auth method:** API key, server environment variable only — never sent to client
**Called from:** server only (`/api/students/:id/report/draft`)
**Key operations:**
  - Single-turn completion: system prompt built from lesson/attendance summary + rawNotes, returns draft text
**Failure handling:** timeout/error → 502, client falls back to manual text entry, never blocks report export

## 7. Performance Strategy

### Caching
- Class lists, rosters, schedules: TanStack Query with a short stale time (30s) — this is a small, low-traffic app, freshness matters more than cache hit rate
- Journey data: cached per `(studentId, classId)`, invalidated whenever Log Session writes to that class
- Never cached: anything parent/student-facing that touches another family's data — not a caching concern, an RLS one, but worth stating: no cross-user cache keys, ever

### Pagination
- Default page size: 50
- Strategy: offset-based (simple, and no list in v1 will realistically exceed a few hundred rows — a solo teacher's own students)
- Applied to: Manage Teachers, Academy Schedule (defensive, not urgent at this scale)

### Avatars
- v1 uses initials-based avatars (e.g., "RP" for Raka Pratama) generated client-side — no upload/storage infrastructure needed
- Real photo upload is a P2, not in scope for July

### State Management
- Server state: TanStack Query exclusively — matches Gio's existing stack, no new library to learn under deadline
- Client state: React Context for language toggle and selected center (admin) — genuinely global, small, UI-only
- Rule: server state (classes, students, lessons, progress) is never duplicated into Context/Redux — it lives in the Query cache only

## 8. Error Taxonomy

| Category | Examples | Client behavior | Logging |
|----------|----------|-----------------|---------|
| Validation | Missing student name, empty lesson title | Inline field error, no toast | No log |
| Auth | Not logged in, expired session | Redirect to correct login for the route group | No log (expected) |
| Authorization | Teacher accessing another teacher's session, parent accessing another family's student | Generic 403, no detail on what was attempted | Log with user ID + attempted resource |
| Not Found | Deleted class, invalid session ID | 404 page or inline "not found" | Log with resource ID |
| Conflict | Duplicate teacher email on invite | Specific inline message | Log |
| External Service (Claude) | AI draft timeout | "Couldn't generate a draft — write manually," non-blocking | Log, no alert (expected occasionally) |
| External Service (Drive) | Video upload/link failure | Session still saves, video flagged as missing | Log |
| Server Error | Unexpected exception | Generic error message, never leak stack trace to client | Full stack trace logged server-side |
